## Claude Codeで実装したゲームロジックが「動くけど面白くない」問題

Claude CodeやUnity MCPにゲームのシステム実装を任せると、コードとしては正しく動く。ビルドも通るし、テストも書ける。だが実際に触ってみると「なんか違う」——敵が硬すぎる、経験値カーブがだるい、リソースがすぐ枯渇する、といったバランス面の違和感が残ることが多い。この「動くのに面白くない」現象は、Claude Code側の実装力不足というより、ゲーム開発の要件定義に固有の落とし穴が原因になっているケースが目立つ。

## なぜ機能要件だけでは足りないのか

一般的なWebアプリの要件定義は「入力Aに対して出力Bを返す」という機能要件が中心で、AIエージェントとの相性が良い。しかしゲームロジックには、機能要件を満たしていても体験として成立しない領域がある。「敵を倒すとダメージを与えられる」は機能要件だが、「3〜5手で倒せる強さにする」は数値のペース配分に関わる制約条件であり、これを言語化しないままClaude Codeに実装を任せると、AIは「動く実装」を優先し、体感バランスの調整までは行われないまま出力される。

## 解決策:体験要件を「数値の制約条件」に変換して渡す

対策はシンプルで、感覚的な要件をAIが扱える制約条件に変換してから渡すことだ。

- 「サクサク倒せる」→「雑魚敵の被弾許容回数は2〜3回、討伐時間は3〜5秒」
- 「序盤は苦しく後半は楽に」→「レベル1〜5は与ダメ効率0.8倍、レベル15以降は1.2倍」
- 「詰まらせない」→「所持リソースが0の状態が3ターン以上続かない」

このように上限・下限・比率で書き直すと、Claude Codeは実装だけでなく、数値パラメータの妥当性チェックやシミュレーション用のテストコードまで一緒に提案しやすくなる。要件定義のフォーマットとしては、機能要件の横に「体験制約」という列を追加した一覧を用意し、実装を依頼する前に毎回そこを埋めておく運用が扱いやすい。

## まとめ

Claude Codeにゲームロジックを任せて「動くのに面白くない」となる原因の多くは、AIの実装力不足ではなく、体験に関わる要件が数値の制約条件として言語化されていないことにある。機能要件と体験要件(数値の上限・下限・比率)を分けて要件定義に落とし込むことで、Claude Codeにゲームバランス調整まで含めて任せやすくなる。

---

普段の業務でも、感覚的な要求を条件や制約に翻訳できるかどうかで、AIに渡した後の手戻り量が大きく変わると感じている。ゲームのバランス調整はその翻訳が特に難しい領域で、数値の上限・下限を先に決めておくやり方は、Web開発で非機能要件を洗い出す作業と近い感覚で扱えそうだ。ここを型化できれば、AIエージェントとの分業をもう一段進めやすくなるように思う。
